# yt2bili 多账号上传与单链接任务技术实现方案

版本：v1.0 草案

编写日期：2026-09-23

需求依据：[多账号上传与单链接任务 PRD v1.1](./多账号上传与单链接任务PRD.md)。本文为实现设计，不表示下述模块、接口或迁移已经落地。

## 1. 技术决策与实施边界

继续使用 React + TypeScript + Tauri + Python + SQLite，不新增服务端、消息中间件或外部队列服务。

本次改造采用以下主方案：

1. 一个桌面业务实例保留一个下载 worker、一个校验 worker；按未归档账号动态建立 0～5 个上传 worker，每账号单路。
2. 引入 `account_id`、独立 `task_id`，业务去重使用 `(video_id, account_id)`；真实 Bilibili UID 用于身份验证和跨进程上传互斥。
3. 所有队列任务与状态以 SQLite 为事实来源，内存队列负责执行；数据库提交先于调度通知。重启继续采用 PRD 的手动恢复策略。
4. 每账号上传阶段保留封面和翻译能力，但拆开“素材准备”和“尝试投稿”两个内部动作，解决登录等待阻塞后续预览的问题。
5. 使用 UID 级上传锁、凭据读写保护和间隔检查，移除全局上传锁及全局上传时间。保留现有共享翻译限额。
6. 新任务使用 `work/<task_id>/`；旧任务读取保存的原目录。不同账号不共享同视频素材。
7. 桌面和 CLI 复用业务服务与媒体阶段函数；协议升级为 v2，批量链接入口关闭，所有新建请求显式指定一个账号。

### 1.1 约束与范围差异

- 最多五账号是“每个应用数据目录最多五个未归档绑定”；跨数据目录只提供同 UID 上传互斥及间隔保护，不建设全机账号注册中心。
- 下载、校验各一路是调度实例内约束；不新增跨机器调度。为避免同库恢复互相干扰，同数据目录只允许一个业务执行所有者，详见第 9 节。
- 以指定 PRD 为范围：默认预览、任务创建后不可改投、投稿参数仍来自全局设置快照。`Bug list.txt` 中的账号独立标签/分区/声明/线路/间隔、默认自动投稿、强制退出自动回队等另有要求，与 PRD 不一致，列入第 17 节的对齐事项，本方案不默默混入。
- 本地大模型翻译已有独立方案。本次不实现模型功能，但明确任务外键、数据库版本和翻译限额的接合方式。
- 方案不新增真实投稿权限；工程测试使用模拟器，真实五账号冒烟按 PRD 单独执行和记录。

## 2. 当前代码核对与改造原因

本节于 2026-09-23 重新核对源代码。

- `scheduler.py::Scheduler` 固定创建 download/validate/upload 三个 `queue.Queue`；`active`、`ScheduledJob` 与取消都使用 video_id。账号维度尚未实现。
- `pipeline.py::_download_job` 会按 video_id 查询/创建任务并生成目录，不能仅在 Scheduler 增加账号后继续直接调用这一身份分配逻辑。
- `pipeline.py::_upload_serialized` 使用 `_upload_lock`、`_last_upload_monotonic`；`locking.py::upload_guard` 又使用固定 account.lock/last-upload.json。两层均须改为 UID 隔离。
- `pipeline.py::_submit_ready` 先设置 uploading，再进入锁、续期和间隔等待，导致尚未投稿也被当成不可取消/结果未知。需要移动上传状态的写入边界。
- `desktop_service.py::operation` 先执行 action，再保存去重结果；进程在两者之间退出会留下已创建任务而无操作结果。只校验 method 也无法识别相同 operation_id 携带不同参数。
- `db.py` 当前 schema=1，tasks、desktop_jobs 按 video_id 主键，写入普遍通过自行 commit 的 upsert。需要提供可组合事务和受条件约束的状态更新。
- `desktop_auth.py::LoginSession` 成功后直接写正式 Cookie；`validate_login` 检查格式，但没有核对 token mid、Cookie DedeUserID、在线身份三者相等。
- `desktop_service.py` 的登录与凭据操作使用全局 ensure_idle/ensure_login_finished；`desktop_settings.py::build` 固定一份 Cookie 路径。
- `events.py`、worker 日志和 App.tsx 的列表键/进度/选中项都按 video_id 关联，同视频多账号会串显示。
- `desktop_worker.py`、Rust main.rs 和 App.tsx 均存在协议版本 1 的检查/构造点，必须同批升级。
- Rust `finish_close` 直接退出，Exit 回调仅等待 worker 约 3 秒后 kill。必须先完成业务退出握手，再调用 finish_close，不能用扩大固定超时替代安全退出。
- 当前 biliup 的自由文本参数使用 `--title=...`、`--desc=...`、`--tag=...`，以避免前导连字符被解释为选项；重构命令构建时保留此修正。

## 3. 目标模块与运行结构

```text
React / CLI
    │ 单 URL、一个 account_id；历史操作使用 task_id
    ▼
TaskService + AccountService
    │ 事务校验、参数快照、操作幂等、账号身份
    ▼
TaskStore / SQLite  ←── committed jobs ──→ Scheduler
                                             │
                       download FIFO ─→ validate FIFO
                        1 worker           1 worker
                                             │ account_id
                   ┌──────────────┬──────────┴──────────┐
                   ▼              ▼                     ▼
              AccountLane A  AccountLane B    …    AccountLane E
                1 worker       1 worker              1 worker
                   │              │                     │
           素材准备 / 可取消等待 / UploadCoordinator
                                  │
                       UID 锁 + 身份复核 + 独立间隔
                                  │
                             biliup 子进程
```

建议新增模块，规模保持在现有项目可维护范围：

- `accounts.py`：账号注册、五账号容量、归档恢复、凭据候选文件验证及发布。
- `task_service.py`：GUI/CLI 公用创建、提交、重试、取消、修复、核对；DesktopService 作为协议适配层。
- `upload_coordinator.py`：投稿前检查、UID 锁、间隔、尝试记录、结果归类；不负责下载或翻译。
- `migrations.py`：有序 schema 升级、备份、旧身份映射和迁移检查。
- `identity.py`：严格单链接解析、ID 校验及任务上下文类型；避免 GUI/CLI 各写一套解析器。

保留并改造 `db.py`、`scheduler.py`、`pipeline.py`、`locking.py`、`desktop_auth.py`、`events.py`。不重新实现 youtube.py/media.py 的媒体算法。

配置拆为三种对象：`TaskSettingsSnapshot`（非敏感固定参数）、`AccountIdentity`（account_id/uid）、`RuntimeCredentials`（临执行读取）。禁止把创建时 Cookie 复制进任务快照或持久 Settings。

## 4. 数据模型与事务

### 4.1 身份与唯一性

- `task_id`、`account_id`、`run_id`、`attempt_id` 均由后端生成 UUID；API 不允许客户端指定素材目录。
- `video_id` 仍是 11 位 YouTube 来源标识，只用于来源、查询和去重，不能作为任务主键。
- UID 规范化为非零十进制字符串，拒绝布尔值、负数、空串和异常格式；昵称、显示序号不用于身份验证。
- 同 UID 归档后重新添加，恢复原 account_id 并重新占用名额，避免换 account_id 绕过同账号同视频去重。更换为另一 UID 则创建新身份。
- 历史未确认账号的任务允许 account_id/UID 均为空，仅迁移与导入可产生，不能执行投稿。

### 4.2 账号表的建议 DDL

以下 DDL 描述新表约束；实际迁移脚本应按版本顺序执行，不在每次连接时重设 user_version。

```sql
CREATE TABLE bilibili_accounts (
    account_id TEXT PRIMARY KEY,
    uid TEXT NOT NULL UNIQUE,
    nickname TEXT NOT NULL DEFAULT '',
    remark TEXT NOT NULL DEFAULT '',
    lifecycle TEXT NOT NULL CHECK (lifecycle IN ('active', 'archived')),
    slot INTEGER,
    credential_ref TEXT,
    credential_revision INTEGER NOT NULL DEFAULT 0,
    auth_state TEXT NOT NULL DEFAULT 'unverified'
        CHECK (auth_state IN ('missing', 'valid', 'expired', 'unverified', 'unavailable')),
    verified_at TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (account_id, uid),
    CHECK (
        (lifecycle = 'active' AND slot IS NOT NULL
         AND typeof(slot) = 'integer' AND slot IN (1, 2, 3, 4, 5))
        OR (lifecycle = 'archived' AND slot IS NULL)
    )
);
CREATE UNIQUE INDEX uq_account_slot
    ON bilibili_accounts(slot) WHERE lifecycle = 'active';
CREATE TRIGGER account_uid_immutable
BEFORE UPDATE OF uid ON bilibili_accounts
WHEN NEW.uid IS NOT OLD.uid
BEGIN
    SELECT RAISE(ABORT, 'ACCOUNT_IDENTITY_IMMUTABLE');
END;
```

slot 是名额约束，不是外部账号 ID。`BEGIN IMMEDIATE` 内查找空闲 slot 并插入/恢复绑定；CHECK 与唯一索引兜底并发时的第六账号。失效、待验证和清空凭据不会改变 lifecycle/slot。归档须先确认没有未完成任务和活动 job，归档提交后回收 lane。

### 4.3 任务表重建

新 tasks 保留现有 url、status、原文/译文、uploader、素材路径、bv_id、error、created_at、updated_at 字段，主键改为 task_id，并增加：

- `account_id TEXT NULL`、`account_uid_snapshot TEXT NULL`、`account_name_snapshot TEXT`。
- `binding_state`：bound / legacy_unbound；两个身份字段同时为空或同时非空。
- `work_root`：经过校验的工作根目录；`work_dir` 保存本任务实际目录，不由目录名反推身份。
- `revision INTEGER`：每次持久状态/元数据变更递增；`metadata_revision INTEGER` 标识编辑版本。
- `wait_reason TEXT NULL`、`error_code TEXT NULL`、`cleanup_state`（none/pending/done/failed）。
- 来源导入信息置于单独映射表，避免把旧 video_id 当新 task_id。

数据库约束：

```sql
CREATE UNIQUE INDEX uq_task_video_account
    ON tasks(video_id, account_id) WHERE account_id IS NOT NULL;
CREATE INDEX ix_task_account_status ON tasks(account_id, status, updated_at);
CREATE TRIGGER task_account_immutable
BEFORE UPDATE OF account_id, account_uid_snapshot ON tasks
WHEN OLD.account_id IS NOT NULL AND (
    NEW.account_id IS NOT OLD.account_id
    OR NEW.account_uid_snapshot IS NOT OLD.account_uid_snapshot
)
BEGIN
    SELECT RAISE(ABORT, 'TASK_ACCOUNT_IMMUTABLE');
END;
```

建表时增加 `(account_id, account_uid_snapshot)` → bilibili_accounts(account_id, uid) 复合外键；所有连接启用 foreign_keys。legacy_unbound 的一次性绑定允许 NULL→有效身份，并由受限迁移接口校验；普通更新接口不暴露身份字段。

### 4.4 作业、顺序、操作和尝试记录

将 desktop_jobs 重建为一任务一行的 job 记录，仍可保留原表名以减少模块改动：

- task_id 主键/外键；run_id、owner_session_id；mode=preview/auto/submit/repair。
- stage=download/validate/upload；execution_state=queued/running/waiting/finished/interrupted。
- queue_seq（阶段入队顺序）；assets_state=pending/complete；media_attempts；cancel_requested。
- settings_json（非敏感快照）；original_status（repair 恢复用）；accepted_metadata_revision。
- created_at/updated_at。业务 task.status 与 job 更新必须处在同一事务。

增加单行 `queue_sequence` 计数器，通过同一事务递增分配 queue_seq。进入新阶段、用户重试/确认、坏文件重新下载时取得新序号；仅等待登录/锁/冷却不重排。无需依赖秒级时间戳判断 FIFO。

desktop_operations 保存 operation_id、method、request_hash、result_json、created_at，唯一键为 operation_id。request_hash 对规范化参数生成稳定 JSON 后计算 SHA-256，排除 Cookie/Token。任务操作包括 task_id 与期望 revision；相同请求重发复用原 hash，即使当前状态已前进也应先返回原结果。

新增 upload_attempts：attempt_id、task_id、run_id、account_id、uid、credential_revision、prepared_at、command_started_at、ended_at、outcome、bv_id、error_code。outcome 至少区分 prepared/not_started/submitted/unknown，原始敏感工具输出不入库。

增加 `legacy_task_map(source_id, legacy_video_id, task_id)` 和导入冲突记录；源库 source_id 持久保存，重复迁移/导入稳定映射。迁移旧操作原始结果另存 legacy_operations 归档，详见第 12 节。

### 4.5 写入纪律与提交后调度

保留 TaskStore 的连接锁，提供显式 `transaction()`；内部写方法不得自行 commit。事务尽量短，不包含网络、文件解码、biliup 调用或锁等待。事件在 commit 后发出，避免回调在数据库锁中请求调度锁。

创建过程：

1. 单 URL 解析、参数类型检查与自动投稿登录预检在事务外执行。
2. 事务内先查 operation_id：method/hash 相同返回已存结果，不同返回冲突。
3. 重读账号 active/UID/凭据 revision，必要时要求重新验证；检查 `(video_id, account_id)`。
4. 命中已有任务则保存“已存在”的幂等结果，不创建新 job；否则同时写 tasks、desktop_jobs、操作结果。
5. commit 后唤醒 Scheduler，由调度器读取当前 owner_session 的 queued job，以 `(task_id, run_id, stage)` 去重分发。

“commit 成功、唤醒前退出”不会丢任务：记录已经存在，重启将其变为 interrupted，用户手动继续。“入队成功、返回前退出”也不会创建第二条任务。内存队列只放 ID/run_id，不承担持久事实。

线程领取任务时重新读取 job 并条件更新 execution_state；取消或旧 run_id 的队列项直接跳过。不能对过期 Task 对象执行全字段 upsert 覆盖新取消状态。

## 5. 账号服务、凭据与生命周期

### 5.1 登录和导入

AccountService 管理登录会话，LoginSession 只产生候选凭据，不直接覆盖正式文件。

新增绑定还没有 account_id：`accounts.add` 或 auth.login.start 的新增模式返回 session_id；候选身份验证成功后才创建 account_id。重新登录必须指定既有 account_id。UI 对未绑定会话按 session_id 关联，对已绑定会话按 account_id + session_id 关联。

提交候选前核验：

1. 文件格式、大小和字段类型符合现有 biliup LoginInfo。
2. token_info.mid 与 Cookie DedeUserID 规范化后完全一致。
3. 通过在线登录检查获得 UID，与候选及既有目标 UID 一致；不能只检查 isLogin 或昵称。
4. 会话仍有效、未被取消/替换；账号未归档、容量和重复 UID 检查通过。

首次绑定网络检查失败不占正式名额；重新登录失败保留原凭据。迁移旧 Cookie 可创建已知 UID 的 unverified 账号，这是明确的迁移例外。

### 5.2 文件与数据库的发布边界

采用账号目录下的版本文件，例如 `secrets/bilibili/<account_id>/credentials/<revision-id>.json`，数据库 credential_ref 指向当前版本。PRD 中 cookies.json 是示例；版本文件能避免“文件已替换、数据库事务失败”丢掉原登录态。

流程：候选文件放入受保护临时目录 → 获取 UID 锁 → 复核会话 → 写完整新版本并确保落盘 → 短事务检查容量/版本并更新指针、保存操作结果 → commit → 发账号事件/唤醒 lane。失败不更改旧指针，并删除本次候选；启动清理由本应用创建且无引用的候选/版本，不能递归清空整个 secrets。

候选提交和会话取消使用同一会话同步边界；取消先赢则禁止提交，提交先赢则取消返回已完成，不宣称已撤销成功绑定。网络等待不持有该同步锁。

biliup renew 可能修改其传入文件，因此先复制到账号临时文件，在 UID 锁内续期、再校验 UID、再发布新版本。biliup upload 也使用本次尝试的私有凭据副本；不允许子进程直接修改数据库指向的版本文件。若工具更新登录内容，仅在校验后发布，失败保留可用旧版本并报告状态。

凭据目录仅当前用户可访问；临时副本同样受保护。凭据值不进入 argv、事件、task snapshot、异常或导出日志；argv 仅包含文件路径。DeepL 的系统凭据存储方式保持。

### 5.3 状态与归档

auth_state 使用 missing/valid/expired/unverified/unavailable，lifecycle 独立表示 active/archived。网络失败是 unavailable，不直接判定 expired。自动投稿创建必须在线预检通过；预览只要求存在可识别绑定。

清凭据和归档以 UID 锁保护，获取不到时立即返回 ACCOUNT_BUSY；不等待正在上传的账号后偷偷修改。其他 UID 不受影响。归档先标记禁止新任务的事务状态并再次检查无未完成任务、无活动 job，提交 archived/slot=NULL 后停止空 lane；并发创建要在同一数据库事务中重查 lifecycle。

“未完成”至少包括 ready、failed、cancelled、interrupted、submission_unknown，以及全部排队/运行状态；本期没有显式放弃历史任务功能时，不通过归档绕开它们。若需释放这类账号名额，应先扩展 PRD 的任务放弃语义。

## 6. 调度器与账号上传队列

### 6.1 线程及内存对象

Scheduler 保留 download_queue、validate_queue，新增 `upload_lanes: dict[account_id, AccountLane]`。最多 7 个业务执行线程，登录线程、RPC 线程及子进程监视线程另计。

AccountLane 包含按 queue_seq 排序的 job 集合、Condition、closing 标志、当前执行项及账号等待状态。没有绑定账号时不创建空 lane；账号绑定成功后动态添加，归档成功后仅停止相应 lane。

active 以 task_id 索引，带 run_id；每条 job 从被执行到退出调度持有其 work_lock，包括等待登录的任务。ready、终态、取消或中断时释放。文件锁失败不直接报 submission_unknown，任务进入可解释的失败/等待路径。

### 6.2 共享下载与校验

把 `_download_job` 中“按 video_id 创建任务、查重、分配路径”移到 TaskService。阶段函数接收已经持久化的 Task/Job，下载解析所得 video_id 必须与任务一致，否则拒绝，不能悄悄换源视频。

下载只执行元数据读取、下载和合并；成功事务写 queued_validation，再通知校验队列。校验继续调用现有 media.prepare_upload_video，成功后按 account_id 路由。封面/翻译不移入共享校验 worker。

InvalidMediaError 延续最多五轮：持久化 media_attempts，隔离坏源文件后重新进入下载队尾；取消或进程中断不算损坏媒体重试。每次新的人工 retry 新建 run_id，并按既有重试规则重新开始一轮预算；不把它当无限自动重试。

submit 模式进入共享校验，成功后 assets_state=complete，直接进入账号的投稿候选；不再翻译覆盖编辑。repair 模式完成校验即恢复原业务状态、发 task.repaired，不进入上传 lane。

### 6.3 账号 lane 的两类动作

同一逻辑上传队列内部区分：

- `prepare`：封面、翻译、文本文件同步；成功的 preview 变 ready 并出队，auto 变为可尝试投稿。
- `submit`：仅针对按顺序轮到的 auto/submit，调用 UploadCoordinator；等待账号/锁/间隔时返回 Wait，不在函数里无限 sleep。

这两个动作共用一个账号 worker，不新增一个可并发投稿的隐藏队列。等待项保留原 queue_seq，只把线程让给同账号后续素材准备。

```python
while not lane.stopped:
    # 短锁内取快照，长操作在锁外执行。
    prune_cancelled_and_stale_runs()
    head = earliest_non_preview_submission_candidate()
    if head is not None and head.assets_complete and gate_due(head):
        result = coordinator.try_submit(head)
        if result.is_finished:
            persist_result_and_release(head)
            continue
        persist_wait_reason(head, result.reason)
    candidate = earliest_unprepared_job()
    if candidate is not None:
        prepare_assets(candidate)
        persist_ready_or_submission_candidate(candidate)
        continue
    wait_for_notification_or_next_deadline()
```

earliest_non_preview_submission_candidate 包含尚未完成准备的早期 auto 任务；不能让后到的已准备 submit 越过它。若队首 waiting，则只允许后续 prepare，不允许后续 submit。preview 从不预占投稿顺序；确认后从校验重新入队。

每次素材动作完成后优先重新检查队首投稿，避免连续新任务使可投稿项饥饿。gate_due 根据已有等待原因决定是否重新尝试：登录失效等待账号事件，冷却等待 deadline，锁竞争定时重试，网络验证暂不可用采用有上限的退避；不能每准备一个后续任务就重复请求失败登录接口。账号恢复、取消、关闭、队列新增立即 notify，不持续空转。

已知账号限流时只暂停该账号后续发起投稿。明确的服务端截止时间可到时恢复；无可靠时长时等待用户通过 accounts.resume_uploads 明确恢复，不编造倒计时。恢复只唤醒尚未发起的候选，任何 submission_unknown 仍必须逐任务核对。

共享翻译锁等待应可取消；保留单路翻译，不持有全局 Scheduler 锁。一个账号正在实际翻译时仅占自己的 lane，其他已经准备好的账号可投稿。

### 6.4 状态和恢复

业务状态沿用 PRD；queued_upload 增加 wait_reason=queue/auth_required/auth_unverified/account_busy/cooldown/rate_limited。剩余秒数从账号 deadline 计算，不每 250 ms 写数据库；仅原因变更落库，倒计时通过事件/快照展示。

明确分离 job.stage 与 task.status：upload 阶段可能是 processing_cover、translating、queued_upload 或 uploading。前端统计以实际 status 为准。

异常时按上传是否可能开始归类，不能仅依据 stage==upload 判未知。普通准备失败退出 lane 并释放资源；某次结果未知只冻结该任务，其他任务仍可排队。账号级失效或限流设置阻断原因，仅影响对应账号。

## 7. UID 锁、上传尝试与间隔

### 7.1 锁域和获取顺序

使用当前系统用户的稳定本地状态目录，例如 AppPaths.default().root 下的 `coordination/bilibili/<uid>/`，这个位置不随 CLI 自定义数据目录变化。包含 upload.lock、attempt-state.json；优先稳定目录而非可被清理的系统临时目录。

同 UID GUI/CLI、复制 Cookie 和不同 account_id 都映射相同 lock。先获取进程内 UID mutex，再非阻塞获取 OS 文件锁；跨进程锁失败返回 Wait(account_busy)，不设置 uploading。不同 UID 的锁相互独立。

锁序约定：数据目录执行所有权 → task/work 文件锁 → UID 锁 → 短数据库事务。任何代码不能持有 DB/Scheduler 全局锁等待文件锁或网络；持 UID 锁的账号操作不反向申请 task 锁。事件在提交、释放内部短锁后发布。

不继续持有旧全局 account.lock 来“兼容旧版并发”，否则五账号会再次串行。升级要求退出旧版 GUI/CLI；旧二进制不受新 UID 协议约束，不承诺混跑安全。

### 7.2 try_submit 的严格边界

1. 确认 run_id、task.status、账号归属及未取消；检查素材和元数据版本，构造工具参数。
2. 获取 UID 锁，重读该 UID 的间隔状态；尚未到期则释放锁，返回 cooldown 及 deadline。
3. 读取最新 credential_ref；在锁内做必要的续期/在线身份复核，三处 UID 匹配。网络不确定返回 auth_unverified，缺失/过期返回 auth_required，不计上传尝试。
4. 所有前置条件完成后，在短事务内再次检查取消/版本，以条件更新写 upload_attempts(prepared)、task.uploading。这是取消与投稿的线性化点：取消先提交则不启动；上传先提交则取消返回 TASK_NOT_CANCELLABLE。
5. 将 UID marker 原子写为 inflight，再启动 biliup；实际 Popen 成功时记录 command_started_at。Popen 前已确定失败，可记录 not_started 并恢复可解释状态；进程突然退出、无法证明没启动，则按未知恢复。
6. 等待子进程最终退出，不因客户端 RPC 超时再次创建调用；取得 BV 才记 submitted，其余可能已投稿的结果记 unknown。
7. 实际子进程结束后记录该 UID ended_at，并事务更新 attempt/task。完成标记写入失败时阻止该 UID 后续上传并报检查点错误，不回退为间隔 0；已有 BV 不被改成失败。
8. 释放 UID 锁；取得 BV 且数据库已持久化 submitted 后进行本任务清理。清理不占账号锁，也不延后 ended_at。

使用结果类型 `Submitted(bv)`、`Wait(reason, deadline)`、`NotStarted(error)`、`Unknown(error)`，取代依据异常字符串和 task.status 猜测是否已投稿。biliup 的登录失效/限流错误如能可靠识别，则另外更新账号状态；不可识别时不猜测平台结果。

### 7.3 间隔算法与崩溃标记

账号间隔采用任务快照中的 upload_gap_seconds，默认 20 秒，计时只看该 UID 上一次实际尝试结束。准备、清理和失败预检不重置计时。

进程内使用单调时钟计算 deadline；跨进程 marker 保存 UTC ended_at 并在读取时转换成有界单调等待，基本公式为 `max(0, ended_at + gap - now)`。系统时钟倒退、标记损坏或遗留 inflight 时采用保守等待：确认没有遗留子进程后，以本次恢复时刻为基准至少等待当前 gap，并记录诊断，而非立即投稿。

marker 同时记录 owner_session_id、父/子 PID 与进程创建标识；只允许回收本应用可证实拥有的子进程，不能仅按 PID 杀进程。若标记/进程身份不足以证明旧上传已结束，则保持 account_busy 并提示人工检查，不能以等待一个 gap 代替进程确认。Popen 与 child_pid 写入之间的窗口由进程所有权回收机制兜底，必须在强杀测试中覆盖。

每次获取锁后重新读取 marker，不能依赖之前界面倒计时。进程崩溃后 OS 锁释放但子进程可能仍在运行，需通过第 10 节的进程所有权确保先回收；仅“锁可获取”不足以证明上传已经结束。

当前 biliup adapter 遇证书错误会换线路重试。保留线路选择，但只有能证明失败发生于提交之前时才允许自动换线；不确定是否已提交的输出必须结束本次尝试并待核对。同一逻辑尝试的串行线路回退不并发、间隔从最后一次结束计时。

## 8. 任务目录、日志与清理

创建时固定 task.work_root 和 `work/<task_id>`，后续配置变更不迁移运行任务。旧任务使用已验证的保存路径，禁止重试时重新拼接当前根目录和 video_id。

同视频五账号对应五个互不共享的目录。校验缓存、meta.json、封面、文本、rejected、pipeline.log 都落在任务目录；每份文件仍走现有完整校验规则。

`TaskContext(task_id, video_id, account_id, run_id, cancel, emit)` 替换原只有 video_id 的线程上下文；所有阶段入口显式建立/退出上下文。logger 命名改为 yt2bili.task.<task_id>，日志过滤器读取结构化上下文，不通过视频 ID 正则决定任务归属。

清理函数显式接收 task_id、work_root、work_dir。验证最终解析路径在可信 work_root 下、不是根目录、不是其他 task 目录，拒绝符号链接/重解析点导向外部路径。旧导入路径须先通过受控允许清单；不从未经核验的 JSON 路径递归删除。

提交成功后先写 submitted/BV/cleanup_state=pending，再关闭本任务日志句柄并清理。异常只写 cleanup_state=failed、保留路径，不覆盖投稿状态；手工登记 BV 按 PRD 保留素材。启动后不自动重投，也不将手工登记的素材当作待清理目录。

### 9.2 请求与错误契约

```json
{
```

返回 `{task_id, account_id, created, status}`；命中已有任务时 created=false 并返回原定位。UI 在 URL/账号/模式变化时生成新的 operation_id，网络重发沿用原 ID。

接口清单：

- tasks.get/list/cover/open_folder、logs.tail：task_id 定位，list/tail 可按 account_id 筛选。
- tasks.retry/submit/cancel/repair/update_metadata/resolve：传 task_id、operation_id；需要防并发编辑时附 expected_revision。submit 不接收目标账号覆盖值。

- system.health：协议版本、schema 版本、capabilities、账号容量和队列摘要。
- system.prepare_shutdown/system.shutdown_status：短请求启动退出并查询状态，不用一个超过 90 秒的同步 RPC 等视频结束。

错误统一 `{code, message, details, retryable}`，常见 code：INVALID_SINGLE_URL、ACCOUNT_REQUIRED、ACCOUNT_LIMIT_REACHED、ACCOUNT_DUPLICATE_UID、ACCOUNT_IDENTITY_MISMATCH、ACCOUNT_BUSY、TASK_EXISTS、TASK_STATE_CONFLICT、TASK_NOT_CANCELLABLE、OPERATION_CONFLICT、SUBMISSION_UNKNOWN、PROFILE_BUSY、PROTOCOL_MISMATCH。details 只含非敏感 ID 和定位，不含工具原始响应。

v1 请求整体拒绝并提示升级客户端，不能自动补默认账号。同步更新 Python/Rust/React、preview 模拟器、桌面自检、smoke 脚本及测试中的版本常量。

### 9.3 快照和事件

任务事件带 task_id/video_id/account_id/run_id/revision；账号事件带 account_id/session_id/credential_revision。保持 worker_session_id/event_id。Protocol.emit 应在同一发送锁中分配事件序号并写出，避免多线程获得序号后乱序发出。

### 9.4 CLI 和数据目录所有权

CLI 增加 accounts list/add/archive、login/renew --account、run URL --account、submit TASK_ID、retry TASK_ID、repair TASK_ID；dry-run 仍只准备素材，retry 按 PRD 回预览。拒绝 --file、多 URL、缺账号和 --force 重发。

增加明确的 `--data-dir` 选项供 CLI 选择账号/任务库；默认保持现有 CLI 项目目录，桌面仍使用用户数据目录。CLI 读取原 .env 的非敏感媒体配置，通过公共 snapshot 构造器创建任务；旧 BILI_COOKIES 只用于迁移/导入，不再隐式指定目标账号。

同 profile 的 GUI/CLI 执行入口获取统一 `execution.lock`，持有到调度器关闭；第二个执行实例返回 PROFILE_BUSY，读列表可使用只读连接。这样不会出现 CLI 启动恢复时把正在运行的 GUI 任务改为 interrupted。不同 profile 可独立运行，同 UID 仍由统一锁保护。

已有 video_id 历史参数先尝试唯一解析，多账号匹配时返回 task_id 列表并要求限定账号；不能选第一条。CLI 待核对按 PRD 交由同目录桌面核对流程处理，不因 retry/run 重复投稿。

## 10. 取消、退出及恢复

取消通过事务设置 cancel_requested，并 notify 所属 lane；尚未执行的持久等待项也可取消，不能只查正在运行的线程。worker 在领取、阶段交接、上传线性化点前检查 token/run_id。

取消校验/下载/准备时复用现有进程控制并保留素材；等待翻译锁和账号间隔可取消。任何迟到回调先匹配 run_id/attempt_id，不能把 cancelled 恢复为 queued_upload。

桌面正常关闭：

1. prepare_shutdown 将 Scheduler 设置为 closing，禁止新建/重试/确认及新登录绑定。
2. 取消所有尚未实际上传的 job（含登录/冷却等待），取消登录会话；通知全部 lane。
3. 在途上传保持运行，最多五项；状态轮询显示剩余账号。它们完成后不再启动下一项。
4. 通过活动 job 计数/Condition 等待阶段交接全部收敛，不依次 queue.join 后立即插 sentinel；最后一次性交付停止信号并 join 所有 worker。
5. 关闭 SQLite、刷出日志，报告 shutdown_ready。Rust 在收到该确认后才允许 finish_close；已有约 3 秒的 Exit 清理只用于后台最终收尾。

操作系统强杀属于异常退出，不能保证保存最后一帧进度。Windows GUI 继续使用现有 Job Object；CLI 增加等价的子进程所有权/父进程退出监视。其他平台适配必须在实际发布平台验证，不能只用 Python thread.watch 证明强杀后无孤儿进程。

重启前先确认本 profile execution.lock 可持有、遗留媒体/上传子进程已被回收，再恢复：有可能开始的 upload_attempt 或 uploading → submission_unknown；其余非终态 → interrupted；ready/submitted/failed/cancelled/未知保持；repair 恢复原状态。旧 run_id 不再入队，所有继续操作生成新 run_id。

4. 已有 work_dir 保留；校验旧 work/<video_id> 或已记录的可信根，不符合允许结构的引用清空并标记需重新准备，绝不删除源文件。
5. desktop_jobs 的引用统一改 task_id；未完成执行按第 10 节恢复为中断/待核对。若已有翻译表，沿映射迁移其 FK、保留人工编辑与翻译结果。
6. 旧操作记录没有 request_hash，不能编造新 hash。原始记录归档并登记已用 ID；命中旧 ID 返回 LEGACY_OPERATION_REQUIRES_REFRESH，提示读取对应旧结果/映射任务，不执行动作。新 UI 操作使用新 ID。
7. foreign_key_check、任务数、BV/标题/原路径抽样及唯一约束检查通过后替换表、记录版本、提交；提交后账号凭据版本发布/残留清理使用第 5 节恢复机制。

旧操作“不再执行”是硬约束；不强求把 v1 的 added/skipped 数组伪装成 v2 单任务响应。可通过迁移查询读取保存的旧结果与新任务映射。

### 12.3 导入与归属冲突

导入先只读打开源库，并按 schema 版本规范化；source_id + 原任务标识防止重复导入。账号映射只能根据 UID，不能根据昵称/slot。未知身份进入 legacy_unbound。

账号满额时不自动创建第六账号；允许仅保留来源记录为未绑定，待用户处理容量后再确认。相同 `(video_id, account_id)` 的冲突记录保留到 import_conflicts，返回现有任务定位，不覆盖任一 BV/素材/译文。

导入的新旧路径都经过同一个 path validator；不导入明文密钥。外部素材如沿用原位，记录其经过确认的 work_root 与目录专用性；无法确认独占时禁止自动清理并提示人工处理。

### 12.4 回滚

升级失败回滚事务并保留源库/凭据；新建无引用候选文件可受控清理。已成功升级后回退二进制，必须配套恢复升级前库与凭据备份，先另存升级后数据库；不能只调低 user_version。

备份以后新增任务不会出现在旧库，回滚说明必须明确。新任务目录保留供恢复，不能随回滚批量删除。未完成人工核对的投稿不能因回滚重新执行。

## 13. 与本地翻译方案的接合

- 在多账号先落地时，task_translation、translation_attempts 从一开始使用 task_id；翻译先落地时，任务主键迁移必须带上这两张表。
- 翻译 provider、模型和后处理设置作为 settings_json 的独立子结构保存；刷新翻译配置不能覆盖 account_id、work_root、投稿模式或发布参数。
- 翻译执行限额保持独立，不将其锁并入 UID 上传锁。五个上传 worker 同时请求翻译仍受共享限额约束，已准备好的账号可正常投稿。
- 本功能不强制引入 Ollama，也不为当前方案移除 DeepL 门禁；若翻译方案同时实现，创建前配置检查统一交给其 TranslationService，避免两处相互矛盾。

### 14.2 必须包含的故障序列

1. A 失效且队首 auto 等待，后续 preview 仍到 ready；B～E 同时完成投稿；A 重登后仍按原顺序提交。
2. 第四账号存在时，两个新增会话同时提交，只有一个占第五名额；另一个不留下账号、凭据或 lane。
3. 同 operation_id 创建已 commit、尚未返回时杀 worker；重启重发不重复建任务，也不自动执行旧 auto。
4. 同视频五份文件中 A 成功被清理，B 等待、C 失败、D 待核对、E 正在修复，各自素材完整。
5. 五路上传中关闭窗口，非上传项取消；最后一个上传结束前 Rust 不主动退出，不遗漏队列交接。
6. 复制同 UID Cookie 到不同 profile，同时尝试上传：一个成功取得锁，另一个可取消等待；UID 不同则可并行。

测试使用 Barrier/Event 与假时钟建立确定顺序，避免依赖 sleep 后“应该执行了”的脆弱断言。真实多进程测试使用临时目录，不读取用户现有库或 Cookie。

## 15. 开发任务拆分与交付顺序

### M1：身份、库与迁移

新增 Account/Task/Job 类型、事务 API、账号容量约束、task_id 迁移、legacy 映射和路径验证。交付：可回滚的迁移测试、同视频五账号独立存取、旧记录完整性报告。

### M2：账号与凭据

改造 LoginSession 候选输出、UID 三方校验、版本文件发布、归档恢复、CLI 账号入口。交付：误扫/并发满额/旧会话/崩溃补偿测试，原凭据不被错误覆盖。

### M3：核心任务服务与调度

移出 pipeline 的任务身份分配，接通 task_id 上下文；实现动态 AccountLane、prepare/submit 分离、UID coordinator、冷却和尝试记录。交付：五路同时上传证据、共享阶段峰值、FIFO 与等待/取消测试。

### M4：协议、GUI/CLI 与退出

升级 v2，更新 React 类型与快照合并、账号选择/容量/七通道、CLI 单链接/显式账号，完成 prepare_shutdown 和原生退出握手。交付：前端、源 worker 与原生外壳联调结果。

### M5：回归、导入与发布检查

保留旧媒体用例，执行迁移/恢复/进程与冻结检查，再进行授权五账号真实冒烟。交付：PRD AC-01～AC-31 对照结果、未通过项、回滚步骤及更新后的 README。

M1 是其余模块基础，M2/M3 在数据契约稳定后可安排开发，M4 与最终联调依赖二者。此处是依赖顺序，不对未实施功能给出已完成或确定工期承诺。

## 16. 发布门槛

- 全部新建入口只接受单 URL + 单账号，所有历史写操作以 task_id 定位。
- 五账号容量有数据库约束和并发测试；五路上传确有共同执行时间，单账号峰值仍为 1。
- 不存在全局上传锁残留、video_id 覆盖任务或跨账号清理；任务归属不可在普通接口修改。
- 上传尝试与取消有确定边界；数据库/工具/进程任一崩溃窗口不自动重复提交。
- 升级、导入及回滚保留历史与素材；旧版本混跑明确不支持。
- PRD 31 项验收逐项记录；仅 mock 通过时标注工程验证，真实五账号链路未通过则不得宣称平台验收完成。

## 17. 实施前需要对齐的事项
