# yt2bili 双账号上传与单链接任务 PRD

版本：v1.0 草案  
日期：2026-09-20  
基线：当前工作区代码与桌面第一期 `0.2.0-alpha.1`，包含尚未提交的桌面实现  
文档状态：供产品评审与开发拆分；本文件描述目标需求，不代表功能已实现。

## 1. 需求摘要

项目需要同时管理两个 Bilibili 账号。保留现有的共享下载队列、共享校验队列及媒体处理规则，将唯一上传队列拆为两个账号各自独立的上传队列。用户每次创建任务只提交一个 YouTube 视频链接，并明确选择一个目标 Bilibili 账号。

核心体验：输入一个链接 → 选择账号 A 或 B → 加入共享下载队列 → 共享校验 → 进入所选账号的上传队列。A、B 可以同时上传各自的视频，同一账号始终只能执行一项上传。

“单链接”限制一次创建请求的输入数量，不限制系统中的任务总数。用户可以连续添加多个任务，无需等待上一条结束。

### 1.1 用户已明确的要求

- 同时管理两个 Bilibili 账号。
- 保留现有下载、校验逻辑，以及下载、校验队列。
- 每个 Bilibili 账号分别拥有一个上传队列。
- 一次只能传入一个 YouTube 视频链接。
- 传入链接时必须选择目标 Bilibili 账号。
- 同一视频允许分别提交给两个账号，每次只选一个账号；通过两次创建形成两条独立任务。

### 1.2 本稿采用的产品默认值

以下是为形成可实施方案补充的建议，不视为用户已经确认：

- 最多绑定两个不同的 Bilibili UID；只绑定一个账号时也能正常使用。
- 账号选择每次必填，初始不选中，不自动沿用上次选择。
- 任务创建后固定目标账号；本期不提供队列中改投账号功能。
- 延续桌面端默认预览、可选自动投稿；重试仍回到预览，不自动重投。
- 分区、标签、线路和间隔仍使用现有全局配置与任务快照；间隔计时改为各账号独立。本期不新增账号专属投稿参数模板。
- 桌面与 CLI 的新任务入口均遵守单链接和显式选账号规则；不保留可绕过规则的批量导入入口。

## 2. 当前方案和代码依据

本节是当前实现事实；后续各节为目标需求。以代码为准，不把旧方案中的规划直接视为已有能力。

### 2.1 已有产品与工程基础

- `三期桌面端实现方案.md` 采用 React + TypeScript + Tauri + Python + SQLite，并将多账号同时投稿列为原范围外事项。本 PRD 对该边界做定向扩展，安装包、macOS 等规划不在本次重新定义。
- `desktop/README.md` 与 `第一期开发与验收记录.md` 记录了桌面开发版、默认预览、人工确认、失败恢复、素材修复等能力。验收记录同时说明真实账号和平台链路仍有待补验；不能据此声称双账号平台并发已验证。
- `README.md` 开头仍有早期“下载和封面处理可以并行”的概述；本需求以当前调度代码及 README 后半段的三阶段说明为基线。

### 2.2 当前入口与账号限制

- `desktop/src/App.tsx` 的 `NewTask` 使用多行输入框，支持 TXT 导入，创建请求为 `tasks.create(text, mode, operation_id)`，没有目标账号字段。
- `yt2bili/desktop_service.py::parse_urls` 按行解析、按视频 ID 去重，每批允许 1～200 条。`create` 对已有视频任务直接跳过。
- `yt2bili/cli.py` 的 `run` 支持多个 URL 和 `--file`；单条、批量分别进入 `pipeline.run` 与 `pipeline.run_many`。
- `desktop_service.py` 只有一个登录会话和一份账号状态；`desktop_settings.py::build` 固定使用 `secrets/bili_cookies.json`。
- 修改或登录账号调用全局 `ensure_idle`，任意任务运行时均可能阻止账号操作。双账号场景下须细化这一限制。

### 2.3 当前队列与上传限制

- `yt2bili/scheduler.py::Scheduler` 创建 `download`、`validate`、`upload` 三个 FIFO 队列，每队列一个线程；不同阶段可以并行。
- 校验成功后，封面处理和翻译在上传阶段执行；预览任务在素材准备完成后进入 `ready` 并离开调度，不长期占住队列等待人工确认。
- `tasks.submit` 会先重新进入共享校验队列，再投稿，避免编辑或文件变化绕过校验。
- `pipeline.py` 存在全局 `_upload_lock`、`_last_upload_monotonic`；`locking.py::upload_guard` 还使用当前系统用户范围的固定 `account.lock` 与 `last-upload.json`。
- 因此仅增加第二个上传线程仍会被全局锁和间隔串行化；必须同步拆分上传队列、互斥锁和间隔记录。
- `pipeline.py` 的 `_translate_lock` 仍是全局翻译锁。可保留此行为；双账号独立上传不等于所有素材准备步骤都并行。

### 2.4 当前数据与恢复限制

- `db.py` 的 `tasks` 以 `video_id` 为主键；`desktop_jobs` 也按 `video_id` 保存配置。当前数据库 `user_version=1`。
- 素材通常位于 `work/<video_id>/`；调度活动表、前端列表键、进度、日志与详情请求都以 `video_id` 区分任务。
- `scheduler.py` 启动时将非终态任务恢复为中断/待核对，不会自动续跑所有任务。它保存任务和快照，但不是能够完整恢复 FIFO 顺序的持久队列表。
- 当前取得 BV 号后清理本任务素材；无 BV 或上传异常进入 `submission_unknown`，保留文件。手工登记 BV 则保留素材。

## 3. 目标、范围与完成定义

### 3.1 目标

1. 用户可辨认并管理两个账号，不依赖覆盖同一 Cookie 文件切换身份。
2. 每个新任务的目标账号从创建到投稿、重试、历史记录都明确且不改变。
3. 账号 A 的上传、间隔等待、登录失效不串行阻塞账号 B 的上传。
4. 下载和校验仍各只有一个工作通道，保持现有媒体安全规则。
5. 升级保留已有任务、素材、BV 号和恢复能力。

### 3.2 本期范围

- 双账号绑定、状态展示、独立登录/续期/清除凭据。
- 单链接输入、目标账号选择、前后端及 CLI 一致校验。
- 两条独立上传队列、账号级互斥、账号级间隔与异常隔离。
- 任务身份、文件隔离、事件与日志、列表及详情的账号维度。
- 旧数据迁移与旧项目导入兼容。
- 对应回归用例、桌面交互验收与经授权的真实账号冒烟验证。

### 3.3 本期不包含

超过两个账号、一次选择两个账号投稿、批量链接/TXT 导入、队列拖拽优先级、任务中途改投、跨账号素材共享缓存、账号独立翻译密钥、自动切换账号兜底、平台审核自动追踪、云端同步、安装器与签名交付。

### 3.4 成功标准

模拟环境能够证明：下载同时执行数 ≤ 1、校验同时执行数 ≤ 1、A 上传同时执行数 ≤ 1、B 上传同时执行数 ≤ 1，且 A/B 两次上传有真实时间重叠。串账号、同账号重复创建、错误清理另一任务文件均为发布阻断问题。

这里约束的是单个桌面调度实例的下载与校验通道；现有 CLI 独立进程并不自动与桌面共享同一条下载队列。本期不扩展为跨机器或跨数据目录的统一调度系统，但同一系统用户下的账号上传互斥必须跨进程有效。

## 4. 核心用户流程

### 4.1 首次配置与添加任务

1. 在“账号与连接”中绑定账号 A；可继续绑定账号 B，也可只使用 A。
2. 打开“添加任务”，粘贴一个 YouTube 视频链接。
3. 从两个账号中明确选择一个，显示昵称、UID 和登录状态。
4. 选择“准备素材并预览”（默认）或“自动投稿”，保留已有转载授权确认。
5. 点击“加入队列”，成功后看到任务与目标账号，系统继续允许添加下一条。

### 4.2 预览后投稿

任务下载、校验后进入目标账号的上传阶段完成封面和翻译，随后停在“待预览”。用户编辑并确认“投稿到【账号昵称 / UID】”，任务重新进入共享校验队列，通过后重新排入该账号上传队列。

确认前的等待不占上传通道；确认后按重新入队时间排队，不保留先前位置。

### 4.3 双账号并行示例

用户依次添加 V1→A、V2→B、V3→A、V4→B。下载与校验仍按各自队列顺序处理。V1 正在上传时，V2 一旦准备就绪，B 可开始上传；V3 必须等待 A 的 V1 结束及 A 的上传间隔，V4 同理等待 B。V1 上传缓慢不妨碍共享下载、校验继续前进。

### 4.4 账号失效与恢复

A 登录失效时，A 待投稿任务保留并显示“等待账号登录”；B 继续。用户重新登录同一个 A 的 UID 后，A 中尚未发起投稿的自动任务可按原顺序恢复；`ready` 仍需确认，`submission_unknown` 仍需人工核对，不随登录成功自动重投。

## 5. 功能需求

### FR-01 单链接输入与创建校验

- 新建弹窗改为单链接输入，删除多行批量说明和 TXT 导入按钮。
- 首尾空白可去除；出现多个链接、多条非空行或混入文字时整体拒绝，不能只取第一条，不能按视频 ID 去重后把“两条相同链接”当成合法单条。
- 继续接受现有支持的视频形态：YouTube `watch?v=`、`youtu.be`、`shorts`、`live`、`embed`，统一提取 11 位视频 ID 并规范化 URL。
- 带单一视频 ID 的播放列表上下文链接仅处理该视频，丢弃列表参数；纯播放列表、频道、搜索页、非 YouTube 域名及歧义视频参数拒绝。
- 仅接受一个 URL 和一个有效 `account_id`；账号不能为空，不接受账号数组，不隐式回退到 A。
- 表单出错保留链接、账号、模式与已填内容，并在相关字段显示原因。
- 服务端必须执行同样的校验；禁用按钮不是唯一门禁。校验失败不创建半成品任务、不开始下载。
- `files.read_urls` 从新建任务能力中移除；旧批量请求返回可理解的兼容性错误。

建议提示：“每次只能添加一个 YouTube 视频链接，请分别添加。”“请选择本次投稿的 Bilibili 账号。”

### FR-02 双账号管理与身份绑定

- 账号页显示两个位置，空位展示“添加账号”；已绑定项展示昵称、UID、登录状态及账号备注。备注仅用于辨认，不承担身份识别。
- 一个账号使用稳定的内部 `account_id`，并绑定真实 Bilibili UID。昵称变化不影响队列和历史归属。
- 两个位置不能绑定同一个 UID；扫描/导入后发现重复，应保留原凭据并拒绝新增绑定。
- Cookie 分账号保存，例如 `secrets/bilibili/<account_id>/cookies.json`；界面、任务快照和日志不得包含 Cookie/Token。
- 账号状态至少区分：未绑定、已登录、待验证、登录失效、验证暂不可用。网络失败不能直接等同于凭据过期。
- 首次绑定须确认凭据身份一致且可识别 UID；不能把无法确定身份的 Cookie 当作任意账号接纳。
- 登录/导入使用临时凭据，校验 UID 后原子替换正式文件。旧二维码回调必须同时匹配账号及会话 ID，不得覆盖另一账号或新会话。
- 已绑定账号重新登录只接受原 UID；误扫另一 UID 时提示并保留原绑定。更换账号身份不是续期行为。
- 本期可仅支持一个可见扫码流程，但操作 B 的登录流程不能阻止 A 的下载、校验或上传。
- A 正在上传时，禁止覆盖、清除 A 的凭据；允许操作 B。A 仅有排队/下载/校验任务时，可登录同 UID，待投稿阶段使用其最新有效凭据。
- 清除凭据保留账号身份、历史及待办任务，相关待投稿任务转为等待登录。清除前说明影响，并在实际修改前重新核查是否已开始上传。
- 更换绑定 UID 仅在该账号无未完成任务时提供；原账号归档，历史保留原 `account_id`/UID，新绑定生成新身份。最多两个未归档账号，不能复用旧身份覆盖历史。
- YouTube Cookie 与 DeepL 仍为共享配置，沿用当前全局修改约束。

### FR-03 目标账号选择与固定

- 每次新建任务必须主动选择一个账号；只有一个账号也不能跳过该字段。
- 未绑定位置不可选；有已确认 UID 但凭据失效的账号可以接收预览任务，并提示“素材可准备，投稿前需重新登录”。
- 自动投稿新建时要求目标账号登录验证通过；验证暂不可用时可重试验证或改为预览，不静默切到另一账号。
- 创建时保存 `account_id` 和 UID 身份快照；昵称可缓存用于历史展示。
- 任务创建后不支持修改目标账号；详情、确认投稿、重试、修复、核对 BV 均使用原绑定。
- `tasks.submit` 不接收任意新目标账号。若客户端传入与任务不符的账号，拒绝操作。

### FR-04 任务去重与重复请求

本条落实已确认的“同一视频允许分别提交给两个账号，每次只选一个账号”：

- 同账号、同视频仅有一个任务记录。不同链接形态解析到相同视频 ID 时也视为重复。
- 重复创建返回已有任务定位信息，不重复下载/上传；失败、取消、中断任务从原记录恢复。
- 同视频投向另一账号可以创建独立任务，互不覆盖标题编辑、进度、BV、错误、文件和日志。
- 已提交或待核对任务不可通过重复创建绕过去重；本期不新增强制重复发布入口。
- 创建请求保留 `operation_id`。同 ID、同参数返回原结果；同 ID 改账号/URL/模式须报冲突。
- 创建任务与保存操作结果应在一致性边界内完成；即使请求超时、连点或 worker 在返回前退出，也不能创建第二份任务或重复入队。

### FR-05 队列、顺序与并发

```text
单链接 + 一个目标账号
          │
          ▼
共享下载 FIFO（1 路）
          │
          ▼
共享校验 FIFO（1 路）
          │ 校验通过，按任务保存的 account_id 分流
          ├──────────────────────┐
          ▼                      ▼
账号 A 上传 FIFO（1 路）    账号 B 上传 FIFO（1 路）
封面 / 翻译 / 预览或投稿    封面 / 翻译 / 预览或投稿
独立账号锁与间隔            独立账号锁与间隔
```

- 下载、校验的职责与并发数不变，完成一个阶段立即交给下游，不等待下游结束。
- 校验通过后只进入任务绑定账号的上传阶段。校验失败仍隔离坏文件、回下载队列尾部，最多五轮下载/校验。
- 每个账号队列按进入该阶段的时间 FIFO；重试、重新确认、重新校验后进入队尾。不保证原始创建顺序永远等于最终投稿顺序。
- 账号上传通道包含现有的封面处理与翻译；预览任务完成准备后离开通道并停在 `ready`。全局翻译锁可保留，但不得以全局上传锁把两个账号再次串行化。
- 登录失效不应阻止预览素材准备。自动任务准备完成后若不能投稿，转入该账号的持久等待列表，释放执行线程；该账号后续素材仍可准备。
- 同账号已经具备投稿条件的任务不能越过更早、仅因登录/冷却/账号锁而等待的任务；需登录的等待任务按原入队顺序恢复。待人工预览的 `ready` 不占投稿顺序。
- 单个任务失败或待核对后应释放通道，允许后续任务处理；若确认为账号整体失效/限流，则只阻止该账号继续发起投稿。
- 队列项和等待原因保存在任务/作业记录中，不依赖界面保持打开。重启语义按 FR-09，不因此扩展为自动续投。

### FR-06 账号级互斥与上传间隔

- 同一账号在桌面内部最多一个上传调用；同一系统用户下 GUI 与 CLI 也不得对同一真实 UID 同时上传。
- 锁以真实 UID 区分，不能只按 A/B 位置、内部账号 ID 或 Cookie 路径区分；复制同一个账号的 Cookie 不能绕过互斥。
- A 与 B 使用不同进程内锁、跨进程锁及上次尝试结束时间。当前固定 `account.lock` 与全局 `_upload_lock` 必须对应改造。
- 默认仍为 20 秒，按“该账号上一次上传尝试结束”计算；成功或失败的实际尝试都更新计时，预览、账号校验失败、取消尚未发起的投稿不消耗一次上传尝试。
- 沿用全局间隔配置和任务参数快照；两个账号计时独立。素材准备已消耗的时间算入等待，不再叠加完整间隔。
- 间隔中展示该账号剩余时间，允许取消尚未开始上传的任务。等待不占用共享下载/校验通道。
- 跨进程账号锁占用时显示“账号正在被另一进程使用”，可等待或取消；不能当作已经发起投稿并直接标记结果未知。
- 开始实际上传前，在同一账号锁保护下重新核查：目标 UID、最新凭据身份、任务状态、取消状态和账号间隔，随后记录尝试并调用 biliup。
- 不以并发数设定保证平台一定接受两路上传。平台拒绝、网络和带宽问题按账号/任务记录，不能自动换账号重投。

### FR-07 下载、校验与素材规则保持

- 保留 yt-dlp 元数据解析、下载、合并和 `.part` 续传，不能把未完成文件当成成品。
- 完整音视频校验、时长与轨道检查、GPU 优先/CPU 复核规则保持。
- 校验缓存继续依赖整文件 SHA-256、文件状态、预期时长、解码模式、规则及工具状态，不能只凭文件存在跳过。
- 完整 MP4 复用原文件，不强制重编码或降低分辨率；非 MP4 按现有规则处理。
- 五轮校验重试上限、坏文件隔离、无效素材禁止进入投稿保持。
- 上传成功取得 BV 后才清理当前任务素材；失败、无 BV、未知结果保留文件。清理失败不把已提交改成上传失败。
- `repair` 继续只准备替换素材、不再投稿、不改写原 BV，并保留所属账号。
- 当前低磁盘空间门禁保留；双账号文件隔离可能增加占用，界面继续展示容量及明确错误，不静默删除其他任务素材。

### FR-08 确认投稿、重试与结果核对

- 预览确认按钮和确认框必须显示目标账号昵称与 UID，避免只显示泛化的“确认投稿”。
- 确认投稿继续进入共享校验队列；复用已经编辑的标题/简介，不重新翻译覆盖编辑。
- 下载、校验或素材处理失败：保留目标账号和素材，手动重试后回到预览流程。
- 实际上传开始前发现无凭据、UID 不匹配、锁占用：进入明确的等待/阻止状态，不伪装成上传结果未知。
- 一旦可能产生平台提交，异常退出、超时或没有解析到 BV 都进入 `submission_unknown`，禁止盲目重试。
- 核对界面明确提示“请核对【账号 / UID】的创作中心”，由用户登记 BV 或声明未提交。打开系统浏览器不代表浏览器一定登录了目标账号，必须保留该提示。
- 手工登记 BV 保留当前人工确认方式，不宣称系统已经验证 BV 所属账号；记录核对账号与操作时间，素材继续保留。
- 确认未提交后回到可手动恢复状态，仍绑定原账号；另一账号的同视频任务不受影响。
- 已提交仅代表平台接收了投稿，不显示为“审核通过”。

### FR-09 取消、关闭与重启

- 下载、校验、准备、排队、等待登录/间隔的任务可以取消，保留可恢复素材并释放相关队列资源。
- 真正调用上传后不提供普通取消，以免产生无法核对的结果；退出时等待 A、B 两个正在上传的任务，而不是只等待一个上传任务。
- 关闭调度时防止队列间转移与退出信号竞态，不能遗漏另一个账号的作业或遗留子进程。
- 重启沿用保守恢复策略：`ready`、`submitted`、`failed`、`cancelled`、`submission_unknown` 保持；未发起投稿的非终态任务标记中断并等待手动继续；上传中的任务转待核对。
- 重启后不自动重新投稿，账号登录成功也不自动恢复已经变成中断或待核对的任务。
- 账号归属、任务模式快照、素材路径、BV 和失败信息必须持久保留。修复任务恢复原记录语义。

## 6. 状态、队列快照与界面

### 6.1 状态表达

继续复用 `queued_download`、`downloading`、`queued_validation`、`validating`、`processing_cover`、`translating`、`ready`、`queued_upload`、`uploading`、`submitted`、`failed`、`cancelled`、`interrupted`、`submission_unknown`。

建议为 `queued_upload` 增加结构化 `wait_reason`，至少支持 `queue`、`auth_required`、`auth_unverified`、`account_busy`、`cooldown`、`rate_limited`；必要时附 `remaining_seconds`。未知冷却时长显示等待原因，不编造倒计时。

`uploading` 仅在实际上传调用即将开始时设置；当前 `_submit_ready` 先设 uploading、再获取锁/续期/等待间隔的顺序须调整。实际调用前落库尝试记录，即便极小崩溃窗口被保守归为待核对，也不能自动重发。

### 6.2 任务中心

- 显示四个通道：下载、校验、账号 A 上传、账号 B 上传。每个展示正在处理的任务、等待数量和主要等待原因。
- 未绑定账号的通道显示“未绑定”；账号命名使用昵称/备注及 UID，A/B 只作为位置辅助标签。
- 任务行增加“目标账号”；同一视频属于不同账号的两条记录必须清晰可辨。
- 新增账号筛选“全部 / A / B”，历史任务可显示归档账号，不因归档消失。
- 任务详情增加目标账号、当前队列、等待原因、错误及所属账号 BV 信息。
- 上传间隔分别展示，不使用全局“下一次上传倒计时”。
- 队列统计区分真正上传、素材准备、排队、待人工预览，避免将所有 `active` 项统称为“上传中”。

### 6.3 账号页与首次配置

- 展示两个账号块，独立提供扫码登录、验证、续期、导入和清除凭据操作。
- 操作按钮根据该账号状态启禁用，不能因为另一账号运行就全部不可用。
- 首次配置可完成一个账号，也可跳过登录；没有可识别账号时，添加任务引导先绑定，不能创建无目标的新任务。
- DeepL 和 YouTube 连接维持共享区域。

### 6.4 事件与前端一致性

- 所有任务状态、进度、日志、素材修复、取消与详情查询使用 `task_id` 定位，同时携带 `video_id`、`account_id` 作为展示与筛选信息。
- 账号事件携带 `account_id` 和 `session_id`，不能把 B 的登录回调渲染到 A。
- 队列快照包含共享下载/校验及按账号分组的上传队列、等待项和原因；统计不能只返回一个扁平 `active` 数组。
- 保留现有事件序号、worker 会话标识和轮询快照恢复方式。前端刷新/漏接事件不能产生串任务进度。
- 列表 React key、选中详情、编辑缓存与日志过滤同步从单独 `video_id` 改为 `task_id`。

## 7. 数据与文件需求

### 7.1 账号记录

建议新增 `bilibili_accounts`：稳定 `account_id`、唯一 UID、昵称缓存、备注、绑定/归档状态、凭据位置引用、最近验证结果与时间、创建/更新时间。敏感内容不入普通任务表或快照。

登录会话、凭据读写保护和账号上传调度均明确接受账号标识。投稿身份以保存的 UID 为准，不以昵称或位置推断。

### 7.2 任务记录

- 新增独立 `task_id` 主键，保留 `video_id` 作为来源标识。
- 新增 `account_id`、`account_uid_snapshot`，建立已绑定任务的 `(video_id, account_id)` 唯一约束。
- BV、标题、简介、状态、错误与文件路径继续属于单条任务。
- `desktop_jobs` 改按 `task_id` 关联，并保留目标账号、原模式与非敏感配置快照；不保存 Cookie 内容或创建时的旧登录凭据。
- 上传时读取该账号最新有效凭据，避免排队期间续期后仍使用失效凭据。
- 操作记录增加请求指纹，至少覆盖规范化 URL、目标账号、模式或被操作的 task_id。
- 可增加轻量上传尝试记录：task_id、account_id、UID、开始/结束时间、结果/BV，用于区分未调用与结果未知，不存原始敏感响应。

### 7.3 素材隔离

本期推荐 `work/<task_id>/`，不引入“下载一次、两个账号共享同一目录”的新机制。

- 同视频不同账号各自下载、校验、保存素材；算法和队列不变，代价是可能重复下载与占用磁盘。
- 校验缓存、封面、翻译文件、`rejected/` 和日志均属于该任务目录。
- A 成功清理仅删除 A 的目录，B 即使同视频也不受影响。
- 路径锁、文件打开、封面读取、修复和清理继续检查合法目录边界。
- 现有 `_cleanup_uploaded_files` 从目录名推断 video_id，日志上下文也以 video_id 区分；目录改造时必须一并显式传递任务身份。
- 暂不共享文件、硬链接或跨账号校验缓存；后续若优化须另定义引用计数与清理策略。

## 8. 旧数据迁移与 CLI 兼容

### 8.1 升级迁移

1. 迁移前关闭旧版本及正在运行的 CLI，确保无活动投稿；备份数据库、设置和原 Cookie，备份同样按凭据权限保护。
2. 数据库版本从当前 1 升级为新版本（建议 2），迁移事务失败可回滚；旧程序遇到新库必须拒绝写入。
3. 原 Cookie 有可确认的 UID 时，可据此建立默认旧账号；无法确认身份时仅导入为待验证，不触发投稿。
4. 旧任务生成稳定 task_id，保留来源 URL、状态、译文、BV、错误与原素材路径；同步迁移 desktop_jobs 和操作记录的任务引用，旧操作 ID 不重新触发动作。
5. 原任务没有账号证据，不能仅因当前 Cookie 存在就声称所有历史投稿都属于该 UID。标记“历史账号待确认”；对未完成任务提供一次性选择绑定，对已提交/待核对任务要求结合原账号核对后登记归属。
6. 未确认目标的旧任务可以查看，但不能恢复投稿。迁移不得默认投向新添加的第二个账号。
7. 旧 `work/<video_id>/` 允许原地继续使用；读取已保存的 work_dir，不要求立即移动大文件。新任务采用独立目录，不能复用占用中的旧路径。
8. 迁移后沿用保守重启语义；不自动启动旧队列、不自动重新提交。

历史归属待确认是迁移例外；新建任务始终必须有目标账号。为旧任务绑定时若发现同账号同视频已有任务，提示冲突并保留两份原始记录供处理，不覆盖 BV 或素材。

### 8.2 旧项目导入

`desktop_service.py::import_data` 当前按 video_id 去重并验证 `work/<video_id>`。本期要识别旧/新两种 schema，按目标任务身份与可信路径导入，未知版本拒绝；仍不自动导入密钥。账号无法映射时进入待确认归属，不按昵称猜测对应关系。

CLI 与桌面目前使用不同默认配置/数据目录，该事实保持显式。需要同一任务历史时使用同一配置数据目录或受控导入；不同目录的历史不会自动合并。即使目录不同，同 UID 的跨进程上传锁与间隔仍须生效。

### 8.3 CLI 新建与历史操作

建议命令契约（目标接口，当前尚未实现）：

```text
python -m yt2bili run "https://www.youtube.com/watch?v=abcdefghijk" --account <account_id>
python -m yt2bili run "https://www.youtube.com/watch?v=abcdefghijk" --account <account_id> --dry-run
python -m yt2bili login --account <account_id>
python -m yt2bili renew --account <account_id>
python -m yt2bili list --account <account_id>
python -m yt2bili retry <task_id>
python -m yt2bili submit <task_id>
python -m yt2bili repair <task_id>
```

- CLI 新建只接受一个 URL；多个 URL、`--file`、缺失账号直接报错，不创建任务。
- CLI `run` 保持原有显式执行投稿、`--dry-run` 仅准备素材的习惯，但必须绑定目标账号且遵守相同去重/互斥/间隔规则。
- CLI `retry` 本期统一为先准备素材供确认，避免借重试意外再次提交；提交待核对任务仍禁止。帮助与 README 必须说明这一兼容变化。
- 为形成 CLI 预览闭环，新增 `submit <task_id>`：显示固定目标账号并执行显式投稿，复用桌面提交门禁及重新校验；无论哪个入口，都不得对待核对任务调用 submit。CLI 的待核对记录需经使用同一数据目录的核对流程处理后才能继续，不能通过 run/retry 绕过。
- 旧 video_id 形式的历史命令仅在能唯一解析到任务时兼容；有两个账号任务时必须要求 task_id 或额外账号限定，不能任选一条。
- 旧 `--force` 不能绕过已提交/待核对任务的保护，本期禁用强制重发语义；批量 `run_many` 不再暴露为用户入口。
- CLI 与桌面复用账号解析、任务身份和投稿业务层，不新增第二套媒体实现。独立 CLI 的执行方式不承诺接入另一个正在运行的桌面实例的 FIFO。

## 10. 验收标准

以下均为本期必须验证的行为，不是本次文档工作已经执行的测试结果。

### A. 输入和账号选择

- AC-01：一条有效链接 + 已选择账号成功创建一条任务；空链接/未选账号不创建。
- AC-02：两条不同链接、两条相同链接、同一行两个链接、多行混入文字均整体拒绝；前端、服务接口与 CLI 一致。
- AC-03：支持现有单视频 URL 形态；纯列表/频道/伪造域名拒绝，含视频的列表链接只处理指定视频。
- AC-04：无 TXT 批量入口；CLI 多 URL、`--file` 不能绕过单条约束。
- AC-05：相同 operation_id 重发只创建一次；修改账号或模式后重用该 ID 报冲突。

### B. 身份和任务隔离

- AC-06：两个不同 UID 可绑定；同 UID 不能占两个位置；只配置一个账号也可工作。
- AC-07：同视频同账号的不同 URL 形态命中同一任务；同视频不同账号各有独立任务、编辑内容、日志、进度和 BV。
- AC-08：创建后切换账号页、修改昵称、续期不会改变任务目标；submit 无法改投其他账号。
- AC-09：误扫其他 UID、旧二维码回调、并发导入/登录不会覆盖已绑定身份或另一账号凭据。
- AC-10：A 上传中可登录/续期 B，不能覆盖 A 凭据；仅 A 登录失效时 B 正常运行。

### C. 队列和互斥

- AC-11：使用阻塞模拟器证明下载峰值 1、校验峰值 1、每账号上传峰值 1，并能观测 A/B 上传时间重叠。
- AC-12：阻塞 A 上传时，B 仍可上传，后续任务仍可下载/校验；不存在全局上传锁造成的串行。
- AC-13：A、B 各自 FIFO；某条失败后后续任务继续，失败重试进入队尾，不越过已排队任务。
- AC-14：A 实际尝试结束后未满 20 秒，A 下一次不得开始；B 不受 A 计时影响。模拟时钟验证失败也计时、准备时间抵扣、预览不计时。
- AC-15：同 UID 不同 Cookie 路径、GUI/CLI 两进程不能同时上传；不同 UID 可同时上传；锁等待不误标待核对。
- AC-16：A 等待登录/限流不阻止 B；预览任务能完成素材准备并释放通道，ready 不阻塞后续任务。

### D. 保持媒体与恢复规则

- AC-17：原有媒体安全回归继续通过，覆盖 MP4 不重编码、GPU/CPU 复核、缓存失效、`.part` 不冒充成品。
- AC-18：校验失败最多五轮、退回下载队尾，最终失败不上传、不阻止其他任务。
- AC-19：预览不投稿；确认后重新校验并使用编辑后的元数据；重试回预览且目标账号不变。
- AC-20：A 成功仅清理 A 任务目录；B 的同视频素材、失败素材、未知投稿素材不被删除；清理失败保留已提交状态。
- AC-21：上传无 BV、提交中断转待核对，不自动重投；登记 BV 或声明未提交只影响选中的账号任务。
- AC-22：修复只产生替换素材，保持所属账号和原 BV，无再次投稿调用。
- AC-23：排队/等待间隔可取消；真正上传中不普通取消；退出正确等待两个账号上传并回收后台进程。
- AC-24：重启不自动续投，未完成任务按既定规则恢复；两个账号归属及历史、文件路径均保持。

### E. 迁移、展示和真实链路

- AC-25：旧库升级成功且有备份，失败可回滚；有/无/无效旧 Cookie 均不擅自认定历史账号，不自动发起投稿。
- AC-26：旧目录原地续用、旧/新 schema 导入、同视频双账号冲突处理都不丢任务/BV/素材；旧程序拒写新库。
- AC-27：列表、详情、历史、日志及四通道快照正确分账号；事件漏接后轮询恢复不串进度。
- AC-28：至少覆盖 1024×680、深浅主题、长昵称、一个账号未配置、两个同视频任务并列显示。
- AC-29：自动化模拟无串账号、重复投稿和误清理；经授权后以两个真实账号及有权发布的测试素材完成少量冒烟，分别核对目标账号和 BV。真实投稿测试不能由 CI 自动触发。
- AC-30：模拟通过与真实平台通过分别记录；若缺真实账号验收，只能标记“工程验证通过、平台链路待验收”。

## 11. 实施顺序与发布门槛

1. **数据与身份基础**：先落实账号模型、task_id、目录隔离、迁移和账号凭据校验，提供可回滚升级。
2. **业务和调度**：贯通任务账号参数，拆分上传锁/间隔及两个队列，完善等待和恢复；先用模拟上传证明独立并发。
3. **交互与兼容**：新建单链接表单、双账号管理、四通道展示、CLI、事件与历史查询同步上线，避免前后端契约混用。
4. **完整回归与平台验收**：执行媒体/队列/桌面回归、迁移和退出测试，再进行授权真实链路验证，更新说明与验收记录。

以上是依赖顺序，不是既定工期。同视频跨账号建任务已确认，任务身份及文件隔离应计入改造；历史账号确认流程和其余范围冻结、技术拆分后再估时，避免把它误判为仅增加下拉框和一个线程。

发布门槛：本期 AC 全部有结果，阻断项清零；未完成真实链路验证时明确标注测试版；不把原有桌面一期测试次数直接复用为本次通过证明。

## 12. 待确认项与风险

### 12.1 待确认项

1. **产品入口范围**：本稿按整个项目统一限制，包括 CLI；若仅限制桌面，需要另行明确 CLI 批量模式如何显式分配账号。
2. **账号专属投稿参数**：本期沿用共享参数，后续再考虑每账号不同分区/标签/线路。
3. **是否支持创建后改投**：本期固定账号；若需要改投，必须另定义历史保留、去重冲突和上传前竞态，不仅是更换下拉框。

未确认项不影响理解前三条核心改造：保留共享下载和校验、拆分账号上传、单链接创建时选账号；但实施前应冻结上述范围。

### 12.2 主要风险及处理

- **只拆队列未拆锁**：通过 AC-11/12/15 实测时间重叠，检查进程内和跨进程两层。
- **旧 video_id 假设遗漏**：覆盖存储、pipeline、事件、日志、前端 key、修复和清理的同视频双账号测试。
- **凭据续期串号**：使用 UID 校验、账号级保护、临时文件及会话隔离，不覆盖另一个账号文件。
- **账号故障使全局停摆**：移除 Bilibili 操作中的全局空闲门禁，改为目标账号的上传与凭据保护。
- **历史归属无法证明**：保留待确认状态和原记录，不用当前 Cookie 推断所有旧 BV 的归属。
- **并发与磁盘/网络资源争用**：不承诺两倍吞吐；共享下载、校验仍可能是瓶颈，同视频双账号独立素材会增加磁盘与流量。
- **平台登录/投稿行为变化**：以本期真实冒烟结果为准；未知结果停止重发，不能用自动换账号掩盖失败。
