## 1. 需求与产品边界

用户创建一条 YouTube 视频任务，选择一个 Bilibili 账号，并可勾选“同步上传抖音”。程序复用同一任务的下载、校验、封面和翻译结果，随后分别交给目标 Bilibili 账号上传队列和唯一抖音账号上传队列处理。

“同步”表示同一次任务选择两个投稿目标，不保证同时开始、同时结束或同时过审。两个平台可以并行上传；其中一个失败不会撤销另一个的投稿。

### 1.1 用户明确提出的需求

- 同步开关放在“新建任务”窗口。
- 未登录抖音时，开关不可勾选。
- 只允许绑定一个抖音账号。
- 抖音有独立上传队列，不占用 Bilibili 上传队列。
- 下载、校验、翻译等前序处理与 Bilibili 使用相同管线。
- 沿用现有模式：预览时一起确认；自动模式两个平台分别自动投稿。这一项已在本次对话中确认。

### 1.2 本稿补充的产品默认值

以下用于补全交互和异常路径，可在评审时调整，不能视为用户另行明确确认：

- Bilibili 仍为必选目标；本期不增加“仅发抖音”。
- 同步开关每次打开窗口默认关闭，不沿用上次勾选。
- 自动同步以所需权限和应用场景获准为上线条件。若当前应用只获准人工确认发布，则明确禁用“同步 + 自动”组合，并允许用户切换预览；不能静默把自动模式变成人工模式，也不能把仅能预览的版本视为本需求全部完成。
- 同一个源视频对同一个抖音账号只生成一个投稿记录，即使该视频另行投稿到其他 Bilibili 账号。
- 创建成功后固定平台选择和账号身份，本期不支持给既有 Bilibili 任务补选抖音，也不支持把排队任务改投另一抖音账号。
- 仅复用前序产物，不自动裁成竖屏、不截短视频、不重复翻译、不新增自动二创。
- 真实平台审核追踪、发布数据统计、定时发布、小红书与多抖音账号均不在本期。

### 1.3 外部依赖

本稿以抖音官方 OpenAPI 为实现路径。应用需要获得发布能力，账号需要授予相应权限；“已登录”和“有投稿权限”是两个条件。当前官方上传与创建接口使用 `video.create.bind`，并要求应用申请和用户授权。[官方创建视频说明](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/create-video/video-create)

抖音对代发场景、目标账号关系和用户操作有要求。默认预览确认可以完整展示两个平台的最终内容；自动投稿组合须作为单独场景完成平台确认和实测后开放，仅有通用登录成功不足以开启。[能力使用规范](https://developer.open-douyin.com/docs/resource/zh-CN/dop/operation-standard/platform-capabilities/usage-spec)

权限不可用时，保留现有 Bilibili 功能，抖音入口显示具体原因。不能把网页模拟点击或 Cookie 私有接口作为自动降级路径。

## 2. 当前项目与目标差异

本次核对代码后确认：

- 当前已支持最多五个 Bilibili 账号及各自上传队列，下载和校验各为一个共享通道。
- 封面和翻译目前在 Bilibili 账号通道内执行，需要前移为两个发布目标共同依赖的素材准备阶段。
- 任务由 `task_id` 标识，每条任务拥有独立素材目录；当前任务身份绑定一个 Bilibili 账号。
- 当前投稿结果以 `bv_id` 和单一 `status` 表达，不能完整表达双平台部分成功。
- 当前取得 BV 后会清理任务素材；新设计必须等待两个目标都不再需要素材。
- 当前模式默认预览，另有自动投稿；未知结果须人工核对，程序重启后不会自动续投未完成任务。

本期保留上述 Bilibili 账号容量和下载、校验、翻译规则，扩展账号页、新建窗口、共享准备阶段、发布记录和清理条件。旧多账号文档含更早的实现基线；本稿的现状以本次源码为准。

## 3. 用户流程

### 3.1 首次绑定

1. 用户进入“账号与连接”，在新增“抖音账号 · 0/1”卡片点击“登录抖音”。
2. 打开官方授权页，用户扫码并同意授权。
3. 应用确认账号身份、授权范围和投稿能力，显示昵称及“已登录 / 可投稿”。
4. 新建任务窗口中的“同步上传抖音”变为可选，但不会自动勾选。

### 3.2 新建窗口

推荐布局：

```text
新建任务

YouTube 视频链接       [ https://...                    ]
目标 Bilibili 账号     [ 请选择一个账号                 ]

[ ] 同步上传抖音
    已登录：抖音账号昵称 · 账号标识
    共用下载、校验和翻译，两个平台分别排队上传。

(●) 准备素材并预览     ( ) 自动投稿

[ ] 我拥有该视频的版权或已获得转载授权。

                                      [取消] [加入队列]
```

未登录时保持复选框可见但禁用，并显示“登录抖音后可开启同步上传”和“去登录”入口；进入账号页再返回时保留原表单，开关仍需用户主动勾选。

### 3.3 预览投稿

1. 输入链接、选择 Bilibili 账号、勾选同步、选择预览模式。
2. 完成一次下载、一次正常成功路径的校验、一次封面处理和一次翻译。
3. 展示同一视频，以及 Bilibili、抖音各自最终投稿文案和目标账号。
4. 点击“确认投稿到 Bilibili 和抖音”，冻结本次内容。
5. 复用现有提交前校验/指纹机制，确认文件未变；通过后分别进入两条上传队列。
6. 两个结果分别展示，一边等待登录或限流不会挡住另一边。

“一次”不排除已有的损坏重下、确认前重新校验和用户主动重新翻译；它表示不因多了一个平台而复制整条前处理任务。

### 3.4 自动投稿

已开通自动同步场景时，新建窗口明确显示“素材准备完成后将分别提交到【Bilibili 账号】和【抖音账号】”。创建记录保留用户主动选择、目标账号、模式和参数版本；素材准备后冻结最终内容、执行平台校验并分别入队。

抖音素材超出接口限制、缺少权限或内容需要用户处理时，仅抖音停在可解释状态；Bilibili 自动任务继续。不得为满足抖音限制而静默修改共用的视频或 Bilibili 文案。

## 4. 功能需求

### FR-01 新建开关与登录门禁

| 抖音状态 | 开关行为 | 界面提示 |
|---|---|---|
| 未绑定 / 已退出登录 | 禁用、未选中 | 登录抖音后可开启同步上传 |
| 授权失效 | 禁用、未选中 | 抖音登录已失效，请重新登录 |
| 验证中 / 网络导致无法确认 | 禁用 | 正在验证 / 暂时无法确认登录状态，请重试 |
| 已登录但缺少投稿权限 | 禁用 | 当前账号或应用尚未取得抖音投稿权限 |
| 登录有效且可投稿 | 可主动勾选 | 显示唯一抖音账号身份 |

- 弹窗打开时刷新状态；登录、退出、解绑及权限变化实时更新。
- 勾选后状态变为不可用，应取消勾选并展示醒目提示，要求用户重新确认当前目标后才能继续提交，避免无提示变成仅投 Bilibili。
- 账号在弹窗打开期间被更换，原勾选作废；显示新身份并要求重新选择。
- 服务端创建时再次校验。前端传入已过期身份或能力时，整个新建请求失败，不留下只有 Bilibili 的半条任务；保留表单供用户重新登录或主动取消同步。
- 未勾选同步的请求不查询抖音网络状态，抖音服务故障不能拖慢 Bilibili 单平台任务创建。

### FR-02 一个抖音账号

- 每个当前数据配置最多一个未归档的抖音账号；不同配置不会形成云端统一账号列表。
- 账号身份取授权返回的应用范围 `open_id`，不能使用可变昵称或展示抖音号作为唯一身份。
- “退出登录”清除本配置的可用凭据并暂停未发起的抖音投稿，保留绑定身份、历史和待办，不释放账号位置。
- “重新登录”只接受原身份；误扫其他账号时不覆盖旧绑定。
- 更换账号需要先结束或明确放弃旧账号全部未完成的抖音投稿，且不存在在途请求及未核对结果；Bilibili 分支仍在运行不妨碍更换。
- 更换时归档旧身份，再绑定新身份；历史结果仍指向旧账号，新账号不会接管旧任务。
- 抖音上传/提交在途时禁止退出、解绑及覆盖授权；其他平台账号操作不受影响。
- 不向普通用户要求 Client Secret、Cookie 或手工输入令牌。

### FR-03 共用素材准备

- 同一任务仅保留一份下载源文件、一份正常投稿视频、一份封面，以及一次共用的翻译结果。
- 沿用现有 YouTube Cookie、下载参数、完整解码校验、GPU/CPU 回退、校验缓存及本地优先翻译配置。
- 素材准备由任务级流程完成，不以任一平台登录是否仍然有效为执行条件。
- 任意 Bilibili 上传拥塞不能阻止已经下载、校验的同步任务完成准备并进入抖音队列。
- 抖音专用的时长、大小、文案和封面参数检查属于发布前适配，不再调用下载和翻译。
- 不把横屏判定为不合格，也不把 MP4 容器名视为任何编码都已获平台验证；实际编码兼容性纳入真实账号验收。

### FR-04 平台文案与素材限制

- Bilibili 保持现有标题、简介、来源说明、分区和标签行为。
- 抖音初始文案取共用的中文标题。简介翻译结果仍在详情页展示，用户可将需要的内容编辑进抖音文案；不自动拼入 Bilibili 专属来源尾注、长简介或“转载”标签。
- 抖音预览允许编辑最终文案；此操作不改 Bilibili 内容、不发起第二次翻译。无额外话题生成需求；用户可在文案中手工填写话题。
- 每个发布目标使用自己的不可变投稿快照。编辑待发抖音文案不能改变已提交或在途的 Bilibili 内容。
- 视频、封面等共用文件在任一目标已确认入队后冻结；不提供上传中替换共用文件。文案修订仅限明确未提交的目标，并重新确认。
- 当前公开创建接口列明 15 分钟时长和 1000 字文案限制；上传文档列明总大小 4GB、超过 300MB 必须分片。实现前需复核接口的实际字节口径与边界，不能混用网页端上传上限。[创建接口](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/create-video/video-create)、[上传接口](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/create-video/upload-video)
- 抖音不满足限制时显示具体原因，保留该目标和素材；Bilibili 可以继续。用户可处理文案、稍后重试或明确“放弃抖音投稿”。本期不自动分段、压缩或裁切超限视频。

### FR-05 两条发布分支和队列

- 保持 Bilibili 最多五条账号队列，新增一条抖音队列；每条队列上传并发为 1，总平台上传上限为 6。
- 同一任务的两个平台在各自就绪后独立排队；抖音不以“Bilibili 已成功”为前提。
- 抖音按“已获发布授权且素材检查通过的入队顺序”FIFO；预览未确认项不占位置。
- 单任务失败或待核对后移出活动队列；账号整体失效、配额耗尽或限流时暂停抖音发起新投稿，保留队列顺序。
- 抖音账号恢复后，正常运行期间等待登录的已授权任务可以恢复；未确认预览、用户取消、结果未知及应用重启中断项不会因此自动发布。
- 抖音冷却和限流独立于 Bilibili。可沿用 20 秒作为本地初始间隔建议，但平台配额、服务端退避优先，20 秒不是平台认可的安全频率承诺。

### FR-06 结果与进度

任务列表保留一条主任务，显示目标标识及分平台摘要，例如“Bilibili 已提交 · 抖音上传 42%”。详情页分别提供进度、等待原因、目标账号、提交结果和错误。

| 场景 | 任务摘要 | 行为 |
|---|---|---|
| 两个平台尚未确认 | 待预览 | 查看两个最终内容并确认 |
| Bilibili 完成，抖音排队/等待登录 | 部分已提交 | 保留素材，继续抖音 |
| Bilibili 失败，抖音完成 | 部分已提交 · Bilibili 失败 | 仅重试 Bilibili |
| 任一目标结果未知 | 待核对，并保留另一目标状态 | 先核对对应平台，不能整任务重发 |
| 两个目标均有可信提交回执 | 全部已提交 | 可按清理策略释放素材 |
| Bilibili 完成，抖音明确放弃 | 已结束 · 抖音已放弃 | 不显示“全部成功” |

“已提交”只表示获得可信投稿回执，不代表平台审核通过或公开可见。用户手工登记结果标记为“人工核对”，与接口回执区分。不能将抖音文件上传成功或取得临时媒体 ID 当作作品已提交。

### FR-07 去重与创建原子性

- 沿用 `(YouTube 视频 ID, Bilibili 账号)` 唯一任务规则。
- 抖音额外按 `(YouTube 视频 ID, 抖音应用身份, 抖音账号身份)` 去重；换一个 Bilibili 账号不能绕过。
- 同视频第二次投其他 Bilibili 账号且再次勾选抖音时，拒绝整次新建，提示“该视频已有抖音投稿任务”并提供原任务入口。用户主动取消同步后可创建 Bilibili 任务。
- 相同任务再次创建但同步选择不同，返回“已有任务的投稿目标不同”，不修改旧任务、不补发抖音。
- 失败、取消、放弃及待核对抖音记录仍占去重身份；恢复只能从原目标记录进行。恢复“已放弃”须明确确认，重新准备后回到预览。
- 连点、请求超时重发、并发创建必须只得到同一份任务和目标记录；不能先成功创建 Bilibili 再发现抖音重复。
- 跨配置/跨设备共用同一抖音身份时，本地数据库去重不够；所采用的官方接入服务需保护同源同账号投稿，或明确拒绝重复请求并返回可核对信息。

### FR-08 重试、取消与核对

- 共享准备阶段失败：两个目标都保持未提交，用户从原任务恢复，复用可用素材。
- 单平台失败：仅恢复该目标，默认回到该目标预览；另一平台已成功的结果不可重置。
- 抖音只完成文件上传、尚未调用创建作品时，可安全暂停，按资源有效性决定复用或重传。
- 创建作品请求可能已送达但回执丢失时，进入“待核对”，禁止自动重发创建请求。
- 用户核对为已提交，登记对应作品标识；核对为未提交后，允许回到原记录预览并重试。核对为未提交不是自动再次发布。
- 任务级“取消未开始投稿”只取消尚未开始提交的目标；已完成的作品不删除，在途请求先收敛并保留真实结果。
- 单目标“取消”保留恢复机会；“放弃该平台投稿”是用户明确结束该目标，两者文案和清理后果不同。
- 所有恢复、核对、取消操作须再次检查该目标是否已经进入在途阶段，防止界面状态过期。

### FR-09 素材保留和退出恢复

- 有任一目标排队、等待登录、失败待处理、取消可恢复、中断、待预览或待核对时，不自动清理共用素材。
- 全部目标已提交，或者每个目标均已提交/被用户明确放弃，且没有运行中的读写操作时，才可自动清理。
- 人工登记提交结果延续现有保留素材语义，设置保留标志；后续只有用户明确释放时才清理。
- 清理失败单独提示，不把平台已提交改成上传失败；重试清理不触发重新投稿。
- 正常退出停止新入队，等待已发起的发布请求取得可保存结果；尚未发起的目标保留为中断或取消待恢复。
- 异常退出后，未发起创建作品的目标按中断恢复；已进入创建请求但缺乏结果的目标按待核对恢复。重启不静默续发。
- 已提交 Bilibili、抖音中断的任务恢复时，只处理抖音，不能重复发布 Bilibili。

### FR-10 旧数据与入口兼容

- 旧任务全部视为未启用抖音同步，升级不会新增抖音投稿。
- 历史 Bilibili 账号、BV、编辑过的文案、工作目录、翻译记录和待核对保护均保留。
- CLI 默认仍创建 Bilibili 单平台任务；可提供显式同步选项，但必须经过与桌面相同的登录、权限、去重及模式门禁，不能提供绕过入口。
- CLI、桌面列表和导出结果均可识别双平台状态；旧客户端不能把部分完成误判为成功。

## 5. 验收标准

| 编号 | 验收情景 | 预期结果 |
|---|---|---|
| AC-01 | 无抖音账号打开新建窗口 | 开关显示且禁用；仍能创建普通 Bilibili 任务 |
| AC-02 | 登录但缺少发布权限 | 开关禁用，原因与未登录不同 |
| AC-03 | 可投稿账号打开窗口 | 可勾选，默认关闭，显示正确身份 |
| AC-04 | 勾选后退出、失效或更换账号 | 目标变化明显提示；提交前再次确认；服务端拒绝旧身份 |
| AC-05 | 并发绑定两个抖音身份 | 最多一个绑定成功，无凭据或历史覆盖 |
| AC-06 | 同步任务正常准备 | 下载/校验/封面/翻译计数不因两个目标翻倍 |
| AC-07 | 预览任务就绪但未确认 | 两个平台实际发布调用均为零 |
| AC-08 | 一次确认两个有效目标 | 各进自己的队列，有可观测的并行上传区间 |
| AC-09 | 一个 Bilibili 账号上传长时间阻塞 | 其他任务准备和抖音上传继续 |
| AC-10 | 两条抖音任务同时就绪 | 抖音最大同时上传数为 1，满足 FIFO |
| AC-11 | 五个 Bilibili 账号及抖音都就绪 | 每账号最多一路，总上传不超过六路 |
| AC-12 | 抖音文件/文案超过限制 | 仅抖音显示问题，Bilibili 按模式继续 |
| AC-13 | 抖音授权过期、限流 | 只暂停抖音，不暂停共享准备及 Bilibili |
| AC-14 | Bilibili 成功，抖音尚未结束 | 保留素材和 BV，显示部分提交 |
| AC-15 | 单平台重试 | 成功平台上传调用次数不增加，失败平台回到预览 |
| AC-16 | 同视频换 Bilibili 账号再次勾选同步 | 原子拒绝新建，指向已有抖音任务；不重复抖音投稿 |
| AC-17 | 连点、同操作 ID 重放、改参数重用 ID | 同参数只创建一次；改参数报冲突 |
| AC-18 | 创建作品超时或返回前崩溃 | 待核对，重启/登录恢复均不会自动重发 |
| AC-19 | 核对结果为已提交 / 未提交 | 分别登记结果 / 回到可人工重试，不影响另一平台 |
| AC-20 | 未完成任务尝试更换抖音账号 | 拒绝更换；旧任务不会转给新账号 |
| AC-21 | 平台结果并发返回 | 两份结果都保留，无互相覆盖、提前清理 |
| AC-22 | 两平台结束、失败、取消、明确放弃等清理组合 | 严格遵守 FR-09；人工核对保留标志有效 |
| AC-23 | 升级已有 v3 / 历史数据库 | 无新增抖音任务，历史数据可读，旧成功和未知状态保留 |
| AC-24 | 仅 Bilibili 请求且抖音服务不可用 | 创建、预览、投稿不受影响 |
| AC-25 | 自动同步场景未开通 / 已开通 | 前者明确禁用组合；后者遵循用户选择分别自动入队 |
| AC-26 | 编辑抖音文案或恢复该分支 | 不重新翻译，不修改已确认 Bilibili 内容 |
| AC-27 | 当前共用 MP4 含不同编码、横屏、大文件 | 用授权测试素材验证实际接受情况，不能只凭扩展名宣称支持 |
| AC-28 | 正常退出与异常退出，含一成功一在途 | 成功回执保留；只恢复未完成分支；未知分支不盲重试 |

自动化测试证明本地状态、并发、去重和异常处理；真实账号验收证明官方权限、授权、媒体接收与作品提交链路。两者分别记录，不能互相替代。

## 6. 开发前需要落实的依赖

1. 确认主体及应用实际能申请到 `video.create.bind`，并确认预览/自动两种操作方式分别允许的范围。
2. 确认官方授权回调服务的部署、域名和运维归属；配套实现方案说明其必要性及视频传输成本。
3. 用获准测试账号验证媒体编码、大小/时长边界、分片上传、封面、最终作品回执；官方文档不同页面有历史口径差异，实测后固定能力配置。

这些是正式发布的外部前提；文档和模拟适配器开发可先进行。当前文档没有宣称这些前提已经满足。
